# 设计决策与权衡

本文记录 Reliable Agent Runtime 的主要架构选择、设计理由及能力边界。

## 为什么需要独立的 Runtime

模型可以提出下一步动作，但无法可靠地强制执行预算、权限、持久化和完成条件。因此，这些确定性控制由 Runtime 负责，并在执行过程中保存相应证据。模型负责决策，Runtime 负责约束、执行和验证，两者职责分离。

## 为什么第一版没有使用 LangGraph

第一版直接实现 Agent Loop，使动作校验、事务边界、中断恢复、错误重试和终止语义在代码中保持可见且可解释。这有助于验证 Runtime 的核心契约，也避免将可靠性机制隐藏在框架默认行为中。后续可以在不改变工具、状态和验证契约的前提下接入工作流框架。

## 为什么模型的 `finish` 不等于任务成功

`finish` 只表示模型申请结束任务。Runtime 随后执行测试、Lint、受保护路径检查及其他确定性Verifier；只有验收条件真正通过，任务才进入成功状态。验证失败的证据会重新返回 Agent Loop，用于下一轮决策。

## Docker 执行边界解决什么问题

Docker 提供可复现的非 root、默认断网和资源受限命令执行环境，用于降低测试或静态检查意外影响主机的风险。它不是面向主动恶意代码的完整生产级沙箱；更高风险的部署仍需要独立节点或microVM、Docker daemon 权限隔离、可信镜像来源和宿主机安全加固。

## 中断恢复如何避免重复应用补丁

每个修改动作都会记录动作指纹、执行前工作区哈希和事务状态。服务重新启动后，Runtime 会将当前工作区与执行前状态进行比较，判断中断步骤是否已经产生实际修改，再决定复用结果、继续任务或安全终止，而不是直接重放补丁。

## 为什么数据库保留完整历史，而模型只接收压缩上下文

完整历史服务于恢复、审计和问题定位，模型上下文服务于下一步决策。将两者分离后，系统可以限制每轮模型输入长度，同时不覆盖原始消息、工具输出和执行步骤。大型输出通过内容哈希引用，文件变化后旧读取结果会被标记为失效。

## 为什么策略判断不能只写在提示词中

提示词只能影响模型行为，不能构成强制执行边界。Runtime 在工具执行前根据工具风险、参数、目标路径和任务状态做 `ALLOW`、`DENY` 或 `REQUIRE_APPROVAL` 判定。审批记录与具体步骤和动作指纹绑定，避免审批结果被其他动作复用。

## 对照评测能够证明什么

评测在固定任务契约上对比 Single Call、Basic Loop、Guarded Runtime 和 Reliable Runtime，并分别记录模型完成声明、外部验证结果、失败原因、步骤、延迟和 Token 用量。它能够检验评测链路、失败可见性和控制机制，但不能仅凭一次小规模实验推导模型能力显著提升或生产环境收益。

本轮 Qwen2.5-1.5B-Instruct 实验的主要价值是暴露提前完成、重复动作和连续失败，而不是证明Harness 能弥补小模型的代码解决能力。安全策略的确定性正确性由专项自动化测试验证，真实模型没有发起越界动作时，不能把“未触发拦截”解释为策略成功或失败。
