# Phase 5 技术验收报告：Docker 执行边界与人工审批

## 1. 项目目标与阶段结论

Phase 5 将“模型建议执行动作”与“系统实际执行动作”进一步解耦：Runtime 先由确定性的Policy Engine 判定风险，再决定直接放行、拒绝或暂停等待人工审批；允许执行的测试/检查命令进入临时 Docker 容器，而不是直接继承宿主机环境。

本阶段关注的不是提高模型生成能力，而是控制模型生成结果的执行风险。最终形成了“策略判定—人工审批—受限执行—结果留痕”的完整闭环，使代码 Agent 的关键动作可控、可暂停、可恢复、可审计。

## 2. 已交付能力

### 2.1 执行前策略判定

- 策略输出固定为 `ALLOW`、`DENY`、`REQUIRE_APPROVAL`。
- 输入包含工具名、结构化参数、工具风险等级、工作区保护规则和任务约束。
- 修改 `tests/` 等保护路径会被直接拒绝。
- 依赖/容器配置修改、文件删除、大规模变更和高风险/网络工具需要审批。
- 每个动作生成稳定 SHA-256 指纹，批准不能被挪用于另一组参数。

### 2.2 可恢复的人工审批

- 审批请求与 `task_id + step_id + action_fingerprint` 绑定并持久化到 SQLite。
- 任务进入 `WAITING_APPROVAL` 时，动作尚未产生副作用。
- `POST /tasks/{id}/approve` 只批准指定步骤；恢复运行时只消费一次批准记录。
- `POST /tasks/{id}/reject` 保存拒绝原因，并把结构化 `policy_rejected` 结果放回 Agent消息上下文，使后续推理可以调整方案。
- `GET /tasks/{id}/approvals` 可用于审计审批状态及原因。

### 2.3 Docker 命令执行边界

每次配置命令使用独立的 `docker run --rm` 容器，并应用：

- 非 root 用户 `65532:65532`；
- `--network none`；
- 只读容器根文件系统与受限 `/tmp`；
- 仅挂载当前任务工作区到 `/workspace`；
- `1 CPU / 512 MiB / 128 PIDs` 默认限制；
- Runtime 超时后强制删除容器；
- 工具只接受预先配置的命令名和 argv，不接受任意 shell 字符串；
- 命令输出、退出码、截断标记及沙箱配置进入结构化 `ToolResult`，工作区 diff 和日志仍由宿主 Runtime 保存。

## 3. 关键设计取舍

### 确定性策略独立于模型

风险决策由 Runtime 执行，模型不能通过提示词自行绕过。这样即使模型输出不稳定，保护路径、审批规则和命令白名单仍保持确定性。

### 审批绑定具体动作，而非笼统授权

审批不仅绑定任务和步骤，还绑定包含工具参数的动作指纹。参数发生变化后必须重新判断，避免一次批准被复用于不同操作。审批状态写入数据库，因此服务重启后仍能继续等待或恢复执行。

### Docker 只承载命令执行

补丁应用、状态持久化和审计仍由 Runtime 控制；可能运行项目代码的测试与检查命令进入临时容器。该边界兼顾了工作区变更可追踪性和代码执行隔离，也避免把 Docker 当作完整 Agent Runtime 使用。

## 4. 自动化验收证据

- 验收日期：2026-09-09
- 运行基线：Python 3.11、Docker Engine 25.0.2、SQLite
- 容器基线：基于 `python:3.11-slim` 构建的最小化非 root 执行镜像
- 验证范围：策略规则、审批状态机、持久化恢复、Docker 隔离和资源控制
- 模型依赖：无。测试使用确定性动作序列，避免将模型输出波动混入Runtime 验收结果。

复现命令：

```bash

  -f docker/Dockerfile.sandbox .

python -m pytest -q
```

最终结果：

```text

```

测试覆盖的关键场景：

- 5 个真实 Docker 集成用例证明非 root 与资源配置生效、容器无法访问工作区外的宿主测试文件、网络连接被阻断、超时容器被清理，以及白名单中的正常测试命令可以通过；
- 审批集成用例证明错误 `step_id` 无法批准、批准前文件保持不变、批准后同一动作仅消费一次；

测试仅出现 FastAPI `TestClient` 关于未来 `httpx2` 迁移的上游弃用警告，不影响结果。

## 5. 安全边界与未覆盖范围

这里的 Docker 是工程化执行边界，不应宣传为可对抗恶意代码的生产级安全沙箱。

- 工作区必须可写，否则 Agent 无法产生补丁；恶意命令仍可能破坏该工作区内容。
- Docker daemon 属于高权限基础设施，生产部署不应把 daemon socket 暴露给 Agent。
- 当前实现未覆盖 seccomp/AppArmor 定制、rootless daemon、镜像签名、机密注入隔离和多租户强隔离；这些应由生产平台层提供。
- 基础镜像只带 Python 标准库。真实项目应构建锁定依赖并经过扫描的专用镜像，通过`sandbox_image` 配置使用，而不是在执行阶段临时联网安装依赖。

因此，本阶段的准确能力边界是：实现了可复现、默认断网、资源受限、带人工审批与审计记录的代码检查执行层；Docker 降低了误操作和依赖污染风险，但并未单独解决不可信代码执行的全部安全问题。

## 6. 阶段结论

Phase 5 规划中的核心闭环已经成立：高风险动作会在副作用前暂停；人的决定与具体步骤和动作指纹绑定；拒绝证据可以进入后续 Agent 上下文；正常 allowlist 命令在受限容器中执行；断网、越界读取和超时清理均有自动化证据。

**验收结论：Phase 5 通过。策略判定、人工审批、受限执行和审计留痕已经形成可运行、可恢复并有自动化测试覆盖的完整闭环。**
