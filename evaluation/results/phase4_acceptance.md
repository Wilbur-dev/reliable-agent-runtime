# Reliable Agent Runtime：Phase 4 工程验收报告

## 0. 结论摘要

Phase 4 已把 Agent 任务从单个 Python 进程内的临时状态升级为 SQLite 持久化状态。任务、步骤、消息、工具执行、产物和验证结果均进入关系数据库；服务重启时可以识别中断步骤、重建上下文，并通过工作区内容哈希避免重复已经发生的修改型副作用。

FastAPI 提供创建、运行/继续、查询、步骤轨迹、取消和健康检查接口。最终集成测试模拟“第一次补丁已经执行但进程尚未保存结果就退出”，新服务正确识别文件已变化，没有重放第一次补丁，而是继续第二次修复并以 `VERIFIED_COMPLETE` 完成。

## 1. 持久化设计

SQLite 使用 SQLAlchemy 2.0 映射以下实体：

| 表 | 保存内容 |
| --- | --- |
| `tasks` | 完整任务、状态、终止原因、Runtime 配置和累计指标 |
| `steps` | 序号、动作、状态、结果、幂等键及修改前后工作区哈希 |
| `messages` | 可重建模型上下文的有序消息 |
| `tool_executions` | 工具名、参数、结果摘要、退出码、内容哈希和 diff |
| `artifacts` | 修改文件路径、类型和内容哈希 |
| `verification_results` | Verifier 名称、成功状态、证据和元数据 |

修改型步骤的事务顺序是：

1. 插入 `PENDING` 并提交；
2. 更新为 `RUNNING` 并提交；
3. 执行工具副作用；
4. 保存结果、工具执行、产物哈希并更新为 `SUCCEEDED/FAILED`。

`idempotency_key` 由标准化动作指纹和执行前工作区哈希组成。这样可以区分“相同动作针对相同状态的重复执行”和“代码变化后合理地再次执行相同工具”。

## 2. 中断恢复语义

服务初始化时扫描 `RUNNING` 任务：

- 未完成步骤没有造成工作区变化：标记为 `INTERRUPTED`，清除旧幂等键，允许重试；
- 修改型步骤尚未记录结果，但工作区哈希已经变化：推断副作用已发生，将步骤恢复为 `SUCCEEDED`，保存推断结果并补回模型上下文；
- 任务回到 `PENDING`，后续 `/run` 从未消费的动作继续；
- 已累计的 wall time、token、费用、重试数和工具调用数继续计入预算；
- 历史工具结果继续参与 Verifier，恢复不会丢失完成判定所需证据。

这不是分布式 exactly-once 保证，而是在单机 SQLite 和独立工作区范围内，通过事务、动作指纹与内容哈希实现可说明、可测试的副作用恢复语义。

## 3. API

| 方法与路径 | 行为 |
| --- | --- |
| `POST /tasks` | 创建任务并保存预算、约束、验收条件和运行配置 |
| `POST /tasks/{id}/run` | 开始或继续任务；同一进程内拒绝并发重复运行 |
| `GET /tasks/{id}` | 查询任务状态、终止原因和累计指标 |
| `GET /tasks/{id}/steps` | 查询完整持久化步骤及工具结果 |
| `POST /tasks/{id}/cancel` | 持久化取消状态；Loop 在下一动作边界停止 |
| `GET /health` | 返回服务健康状态及本次启动恢复的任务数 |

不存在的任务返回 HTTP 404；已取消、正在运行或没有剩余动作等冲突返回 HTTP 409。

## 5. 说明

Phase 4 的关键不只是“把对象写进 SQLite”，而是明确崩溃窗口：数据库显示
`RUNNING` 时，工具可能尚未执行，也可能已经修改文件但来不及回写结果。恢复逻辑通过执行前工作区哈希与当前哈希判断这两种情况，从而避免盲目重放补丁。同时明确它是单机工程控制而非分布式 exactly-once，避免夸大系统保证。
